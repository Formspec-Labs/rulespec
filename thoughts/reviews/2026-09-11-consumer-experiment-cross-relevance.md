## Work package 1 — A useful source result with evidence and feedback

**R17/R18 with narrow R24 accounting; estimated effort S–M, roughly 1–2 working days after choosing a consumer.** Intended outcome: a person finds a provision, sees its supporting context and unresolved reference state, and reports the exact reading they dispute.

**Decision and hypothesis:** does expanding evidence after source ranking supply missing governing context without displacing useful provisions? If ranking is the real failure, this intervention will not rescue an unseen provision. That result should trigger a distinct ranking comparison, not larger evidence bundles.

**Reuse:** `records(book, source, 'source'/'packets')` in `P/discovery.py:19–48` gives identical source text/identity with different evidence. `E/discovery_trial.py:28–63` already ranks and checks support. Reuse `export_discovery`'s passage IDs, `statements`, `evidence` and external source tables (`discovery.py:52–138`); source/edition identity must accompany offsets. Use `reference_observation` and the current CLI/store path for submission. A browser route must call this validator server-side against its saved scan; generic `/api/actions` does not itself validate reference-specific identity.

**Arms and constants:** freeze current books, source-reader pins and eight new query/expected-support records before scoring. A returns top-three source hits; B returns those exact same hits plus verified evidence. Keep a 1,500-unique-source-character display budget in both arms, retaining a trace of selected and omitted intervals. Count serialized bytes separately, since unique source characters do not measure repeated JSON. If the budget never binds, this run cannot establish a constrained-context benefit; stop that claim rather than changing the cap after seeing results.

**Cases:** exact citation lookup; ordinary paraphrase; a provision absent from extracted statements; a short list item requiring its lead-in; the beer-cargo duplication mechanism; chlorine or service-equipment rank displacement; a rejected reference; and competing editions/unresolved target. Reuse historical queries only as development controls and label them separately from new queries. Exact lookup is a navigation control using `scan_references`, not evidence that the lexical ranker understands citations.

**Feedback controls:** use accepted and rejected rows, identical mentions at different positions, a changed reading with the same accepted ID, and ambiguous editions. Show the saved challenged reading next to the current scan, then reload/export the observation. Include one truly unrecognized mention as an explicit unsupported-input case; do not fabricate a parser candidate to report it. Use an existing run for this first consumer. A later source-only entry point should record truthful processing status and reuse the store only if the actual consumer needs it.

**Measures and rules:** pre-review all required governing support, then record complete support, distinct useful provisions, duplicate hit slots, unique evidence intervals, omitted context, unresolved states, payload and reader task time. Adopt expansion for this use only if at least two query tasks gain complete support, none loses critical support within the fixed budget, and the feedback controls preserve the exact challenged version without changing scanner results or approvals. Defer if source-only is equally complete and simpler. Stop after eight query cases plus controls, zero provider calls and the two-day effort bound; unresolved questions remain reported.

**Conditional next comparison:** only when the frozen failures are ranking failures, compare source-only against one preregistered rank-based merge of separately ranked source/summary lists, keeping the same evidence policy. Reuse `search`; do not merge its raw scores because each collection has its own document-frequency and length statistics. Source fallback and duplicate crowding remain gates. Feedback is an observation channel for prioritizing such cases, not a relevance label or automatic training signal.

**Dependencies removed:** no embedding/index migration, R8 graph-reader consolidation, R22 vocabulary work, full semantic audit, cross-reprocessing approval transfer or new feedback service. The new CLI capture removes the need to repeat the already retained R18 persistence experiment; consumer display and use remain open.

## Work package 2 — A reviewed preparation draft before a workflow adapter

**R19 with narrow R24 accounting; estimated effort M, roughly 1–2 working days.** Intended outcome: prepare one source-backed decision flow with less total preparation and correction effort, while preserving questions that still require judgment.

**Decision and hypothesis:** can an existing extracted draft reduce preparation effort without hiding a branch or suggesting an unsupported action? The alternative explanation is that a reviewer must reconstruct enough source context that the draft adds correction work.

**Reuse and arms:** A prepares from the pinned source; B prepares from the same source plus an existing saved draft and `export_discovery` evidence. Both produce the same small table of facts, questions, actions, governing conditions, alternatives, deadlines and unresolved choices. Use `E/results/source-review-decisions.json:30–36` to design development scenarios: older name change with unchanged identification, urgent/emergency travel, and the within-one-year documentation branch. Those agent-authored judgments are not expert gold or current legal advice. Choose an untouched comparable source activity before claiming transfer.

**Cases and constants:** six scenarios covering each ordinary branch, both sides of a stated time boundary, an exceptional permission, and one missing/disputed fact. Specify exact anniversary behavior as unresolved unless the source establishes it. Freeze source edition, scenarios, expected support and output template before either draft. Counterbalance assignment/order across reviewers or comparable scenarios; the same reviewer repeating the same task learns from A. If only agent preparation is available, report agent work and correction counts as proxies; human time saved remains unmeasured.

**Adoption/stop rule:** each reviewed scenario must retain every material branch and all required evidence, introduce zero unsupported actions/fields, and leave unresolved facts visible. A provisional 20% reduction in combined preparation-plus-correction time justifies a second activity; a single small sample does not establish general productivity. Stop after six scenarios and two working days. Defer automation if the source-only draft is clearer or quicker after correction. Preserve disagreement and the original labels rather than revising them to make B pass.

**Reuse boundary:** `P/core.py:449–458` already exposes `meaning_assertion_id` and evidence roles; `constraints/core/generated-work-product.cue:3–18` supplies `rkaf:justifiedByAssertion` for a consumer-owned field or step. Use those when a real form/workflow object is created. Do not mistake `logic_text`, an applicability condition, or a qualification target for an executable branch.

**Dependencies removed:** no formspec/wos-spec bridge, general workflow engine, complete document-family benchmark, universal reference resolution or R16 prompt change is needed for the preparation comparison. Activate R16 only for a specific scenario failure. Existing CUE already asks for complete governing scope and distinguishes permission, obligation and responsible actor (`schema_data/document-understanding.cue:22–55`); repeating those requirements is not a new intervention.

## Work package 3 — Independently judge fixed targets, then measure the useful operation

**Conditional R25/R26, or R16 only if the chosen consumer exposes a different error; estimated effort M, roughly 2–3 working days.** Intended outcome: keep a supported qualification link when another proposed target is unsupported, without changing the qualification's complete meaning or hiding disagreement.

**Decision and hypothesis:** one verdict per target will retain distinctions that the existing bundled verdict already explains. A competing explanation is unclear relationship meaning: dividing the verdict may simply produce more confident but inconsistent links. Before the comparison, decide whether each case tests a qualifying exception or the explicit recording of already stated applicability; retain genuinely disputed readings as unknown. Keep original historical expectations intact and label any new interpretation separately.

**Reuse:** the saved targeted harness already uses `_challenge_prompt`, `_call`, `_decode_checks`, source passage references and capture/replay (`X/2026-09-10-design-targeted/experiment.py:31–42,89–110,113–130`). Reuse those mechanics in a new experiment directory, with one shared source/draft request. Keep grouped baseline statements and all their conditions intact. Independent target verdicts do not require splitting every action or making one call per target.

**Offline application check first:** use explicitly constructed verdicts, separately labeled from provider output, to assemble one replacement containing the supported subset plus existing valid links. Pass it through `_action` → `store.preview` → current-revision check → `store.apply` (`P/refinement.py:271–295,324–339,493–527`). Keep every excluded/disputed target's evidence and verdict as an observation. Include a supported-plus-negative pair, `not_required` exemption, repeated target, stale qualification and stale target. Preserve Core's incomplete-target and review's changed-target guards (`core.py:302–316`; `review_store.py:317–331`). A subset must be a new explicit correction, not partial acceptance of a stale saved proposal.

**Future model arms, only after that check:** A is the current bundled judgment; B changes only judgment granularity, with source references, rationale and supported/unsupported/unknown for every supplied target, and no affected-action field. Freeze model/version, actual request bodies, source catalogs, targets, settings and request limits. Use the three original mobile-phone/refrigerant/railroad failures plus one untouched source case with both a supported and an unrelated target. Two observations per arm give 16 calls; preregister a ceiling of 300,000 reported tokens and two elapsed hours, counting incomplete responses and failures. Keep raw evidence for both arms and use blinded output ordering where possible. Do not infer a general error rate from these selected cases.

**Adoption/stop rule:** require recovery of the known supported links lost by mixed bundles in both observations, retention of existing correct links, zero added known-wrong links, explicit unknown outcomes for predeclared disputes, and exact subset application without meaning/approval drift. Stop at the first exhausted bound; a failed or inconclusive gate leaves the change experimental. Historical 4/5 is not the target to optimize, and the previously failed affected-action variant remains deferred.

**R26 follows the named useful operation:** the public full route adds initial audit, recovery/relationships and final audit; `audit_run` itself performs inventory then comparison (`P/audit.py:489–504`; `refinement.py:471–478,551`). Fixed-target experiments can reuse saved packets/current audit material without running that entire route. After R25 earns value, separately compare its bounded operation with the full route on the same named task, counting useful findings, missed issues, new defects, unresolved outcomes and actual usage. Do not claim equivalent broad omission detection. Expose a smaller public function only if a caller needs it and task quality survives at lower total cost; source deduplication and prompt compression are later separate factors.

## Scope of the decision

R17 asks whether a reader can find complete support; R19 asks whether someone can prepare a faithful decision flow. They share source evidence and review records, but have different outputs and success measures. R18 provides feedback provenance, while R24 prevents passing mechanics from becoming a claim of semantic correctness or benefit. R16/R25/R26 are optional responses to demonstrated failures. These packages can produce bounded adoption/defer decisions without closing the broad R24 release-quality task or expanding the default extraction pipeline.
