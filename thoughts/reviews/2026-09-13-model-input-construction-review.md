## What is already sound

The initial extraction prompt explicitly distinguishes instructions from source data, excludes outside knowledge, preserves modal force and governing conditions, permits absent optional structure, and requires a complete default statement. Its invented examples test useful semantic differences: an exception affecting one duty, inherited conditions, an exemption alongside a surviving duty, and background that must not become a prerequisite. These are meaningful examples, even though they are prose rather than example JSON. See [extraction.py:37](/Users/mikewolfd/Work/rulespec/packages/rulespec-extrapolator/src/rulespec_extrapolator/extraction.py:37).

The source catalog supplies actual text beside selectable passage identifiers. The prompts correctly say that locating a passage does not prove an interpretation. Refinement presents source before draft claims, uses short claim aliases, identifies navigation as semantically unassessed, and preserves unresolved references. Structured output definitions carry substantive field descriptions rather than just types. These are strengths to retain.

There is no evidence of context exhaustion here. The three source excerpts contain 382–764 characters. Cell 1 generation has 10,835 content characters plus roughly 17,000 characters of compact schema: much larger than its source, but character counts are not tokens or proof of overload. The observed problem is what the request asks the model to attend to and reproduce.

## Findings that affect the decision

### 1. Optional structure is repeatedly mistaken for missing meaning

Initial extraction explicitly excludes separate action/object extraction, and its `unit_attributes` schema has five required properties among sixteen declared properties. Optional scope and logic may be absent when the statement and evidence suffice. This is intentional behavior, not incomplete extraction. See [extraction.py:135](/Users/mikewolfd/Work/rulespec/packages/rulespec-extrapolator/src/rulespec_extrapolator/extraction.py:135) and [CUE definitions:231](/Users/mikewolfd/Work/rulespec/packages/rulespec-extrapolator/src/rulespec_extrapolator/schema_data/document-understanding.cue:231).

Refinement instead requests all 27 replacement meaning fields. Their descriptions include action being empty when inapplicable or unstated, without explaining that an existing empty action can simply be unassessed by the first pass. The broad recovery instructions remain before the narrower selected-edit task. The latter clearly overrides add permissions; this is not an irresolvable instruction contradiction. It is an unnecessarily broad task surface.

The effect is observable. Cell 4 fills action/object fields without changing either selected summary, and its checker approves those changes as completing missing fields. Cell 1’s checker likewise describes absent action/object fields as defects. Cell 5 preserves the unexplained pension clause pointer while populating components and receives support. See the [cell 4 response](/Users/mikewolfd/Work/rulespec/thoughts/experiments/2026-09-13-explicit-rule-construction/captures/cell-4/generation/attempt-0000.response.json) and [checker response](/Users/mikewolfd/Work/rulespec/thoughts/experiments/2026-09-13-explicit-rule-construction/captures/cell-4/check/attempt-0000.response.json).

The checker already says a component may remain unstructured when meaning is faithful ([refinement.py:95](/Users/mikewolfd/Work/rulespec/packages/rulespec-extrapolator/src/rulespec_extrapolator/refinement.py:95)). The model did not consistently follow that instruction. Repeating it more emphatically is a hypothesis, not an established fix. Reducing unnecessary editable fields offers a more direct experiment.

### 2. Checking a proposal is different from checking the selected reading

The construction arm explicitly demands independently complete selected statements. The checker receives the ordinary `CHECK` instructions, source, draft, and proposed changes, but neither the added construction task nor the selected-alias list. It checks one verdict per proposal, so a mistaken no-op can escape review entirely. This behavior follows [the checker construction:207](/Users/mikewolfd/Work/rulespec/packages/rulespec-extrapolator/src/rulespec_extrapolator/refinement.py:207); it is not a mysterious reasoning failure.

Notice C0000 is a clear example under the declared standalone-reading criterion. Its unconditional-looking pre-filing requirement omits the supplied infeasibility exception. Cell 2 calls it complete because paragraph (1) is unavailable, although the relevant exception is present locally. Only the proposed C0002 edit reaches the checker. An unresolvable remote reference does not excuse omitting a supplied local exception. The [cell 2 request](/Users/mikewolfd/Work/rulespec/thoughts/experiments/2026-09-13-explicit-rule-construction/expected-requests/cell-2-generation.json:3) contains all this source text.

Navigation helps locate outgoing references, but it is not an inventory of governing meaning. Notice navigation includes C0002 → C0001 for clause (i), but not the subparagraph (A) reference from the exemption to C0000. Full source remains available, so the omission is not missing evidence; it is a reason to avoid treating navigation as exhaustive.

### 3. The checker receives an application identifier as though it were proposed meaning

Cell 6’s raw model response selects `qualifies: ["C0000"]`. The application converts this to a revision identifier in `fields.applies_to` ([refinement.py:302](/Users/mikewolfd/Work/rulespec/packages/rulespec-extrapolator/src/rulespec_extrapolator/refinement.py:302)). The checker receives that full identifier alongside the alias and criticizes it for lacking a basis in the statute. Identity bookkeeping need not occur in statutory text.

That is a concrete presentation defect. Omit redundant application metadata from the semantic view or render the relationship consistently through supplied aliases. The same checker also correctly objects to an action/object mismatch, so removing this defect does **not** establish that the rejected proposal should pass. See [cell 6 checker input](/Users/mikewolfd/Work/rulespec/thoughts/experiments/2026-09-13-explicit-rule-construction/expected-requests/cell-6-check.json:3).

### 4. Re-emitting optional evidence creates avoidable failure opportunities

Cell 3 writes a faithful pension summary but supplies `logic_text` that drops the source’s `(II)` marker. That field is defined as verbatim evidence, so the rejection is justified. The full replacement fails even though the intended summary repair is good ([validation:298](/Users/mikewolfd/Work/rulespec/packages/rulespec-extrapolator/src/rulespec_extrapolator/refinement.py:298)). This supports testing a smaller response interface, not relaxing quotation fidelity or silently editing captured answers.

## Where I would qualify the scoring

Source fidelity, completeness of a document’s retained meaning, and usability of one record without its neighbors are separate properties. An exact clause pointer can preserve source meaning while failing the last property. Neither passage matching nor a supported edit proves that every selected record is independently usable.

The pension eligibility expansion and notice C0000’s missing exception are strong cases for construction. Other labels depend more heavily on the chosen product boundary. The electronic-request permission can remain a faithful permission while a separate record requires name and reference number. Combining them is useful for an independently usable action description, but should not imply that failure to include those fields extinguishes the permission unless the source establishes that consequence.

Similarly, an exemption record should identify what duty is waived. Requiring it also to restate every surviving independent duty is a broader completeness policy, not automatically the semantic meaning of the exemption. If required for safe independent display, say so in both generation and checking. Preserve the surviving duty without presenting its compliance as a prerequisite for the exemption. The [anonymous review:100](/Users/mikewolfd/Work/rulespec/thoughts/experiments/2026-09-13-explicit-rule-construction/ANONYMOUS-REVIEW.md:100) acknowledges this record-boundary choice; I agree that its strict scores are product-specific and revisable.

## What current provider guidance supports

**Exact Gemini model guidance exists.** Google’s [Gemini 3.8 Flash guide](https://ai.google.dev/gemini-api/docs/latest-model), updated **3 September 2026**, explicitly identifies `gemini-3.8-flash`, medium default thinking, and low/medium/high options. It directs callers to remove `temperature`, `top_p`, `top_k`, and `candidate_count`. Saved requests include `temperature: 0` and `candidate_count: 1`; [the provider construction:513](/Users/mikewolfd/Work/rulespec/packages/rulespec-extrapolator/src/rulespec_extrapolator/extraction.py:513) supplies both. Successful captures establish that these arguments reached the SDK call and a response returned, not that the server honored deprecated sampling controls. Treat this as compatibility cleanup, not a proven cause of semantic failure. The textual `Q:`/`A:` suffix is inside one content string; it is not a prohibited prefilled model-role turn.

For **general Gemini 3.x prompting**, the [3.5 developer guide](https://ai.google.dev/gemini-api/docs/generate-content/whats-new-gemini-3.5), updated **30 July 2026**, recommends concise instructions and the specific task after lengthy context. Google’s [prompt-design guide](https://ai.google.dev/gemini-api/docs/prompting-strategies), updated **10 June 2026**, permits critical constraints in a system instruction **or at the beginning of the user prompt**. Thus absence of `system_instruction` is not itself incorrect. Testing stable rules in that role and a short task after the source is reasonable; no observed failure proves placement caused it. The same guide recommends varied examples, but its literal fact-reporting template should not be copied wholesale into a task that must resolve supplied cross-references and express their implications.

Google’s [structured-output guide](https://ai.google.dev/gemini-api/docs/structured-output), updated **2 September 2026**, supports descriptions, explicit required fields, and nullable types, while distinguishing syntactic conformance from semantic correctness. Existing CUE descriptions and honest empty states follow that guidance.

For **recent OpenAI models**, the current [GPT-5.6 guide](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.6) recommends removing one group of repeated instructions at a time and retaining examples that encode real requirements. Its coding-agent efficiency results are not evidence of a Rulespec extraction gain. The current [Astra guide](https://developers.openai.com/api/docs/guides/latest-model) emphasizes sensitivity to conflicting instructions and requires model-specific reasoning settings; it does not establish an optimal extraction effort. Keep provider and effort comparisons separate from prompt comparisons.

OpenAI’s [prompt-engineering guidance](https://developers.openai.com/api/docs/guides/prompt-engineering#message-roles-and-instruction-following) supports application instructions in `developer`/`instructions` and variable source input separately. Its [reasoning guidance](https://developers.openai.com/api/docs/guides/reasoning-best-practices#how-to-prompt-reasoning-models-effectively) recommends straightforward goals and trying zero-shot before examples where appropriate. That differs from Google’s general preference for examples: neither licenses deleting Rulespec’s useful examples without evaluation. Brief source-based rationales are useful review outputs; demanding a long reasoning transcript is unnecessary.

OpenAI [strict Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) requires every declared field to be required, using null unions for optional values. Gemini’s extraction schema permits omission. Therefore **all-required is not inherently defective**; the concern is making the model regenerate unrelated content. Any OpenAI comparison needs a provider-compatible schema with equivalent meaning and absence behavior, rather than sending the Gemini schema unchanged.

## Ranked next steps and a controlled test

1. **Align the evaluated task.** Specify which incoming qualifications and surviving duties belong in a standalone reading. Apply that same criterion to generation, proposed edits, and selected no-ops. Keep optional enrichment distinct from successful repair.
2. **Correct checker presentation.** Preserve aliases consistently and separate application-generated identities from source-derived meaning. This is independently justified by the captured misattribution.
3. **Test a bounded response.** Compare full replacement against a selected-summary-and-support response whose unchanged fields are retained deterministically. Derive definitions from CUE and preserve current evidence validation. Do not turn this into a general patch language.
4. **Conform provider settings, then test layout separately.** Remove deprecated Gemini parameters in a future authorized change. Do not combine this with changed effort, examples, source selection, and response shape in one claimed causal comparison.

A clean next experiment would use the same explicit task and checker policy in both arms, with the response interface as the only intentional treatment. Freeze eight new source excerpts, two repetitions per arm, model/effort, source text, selected claims, navigation, and acceptance labels before generation. Normalize both arms into the same complete candidate representation before checking. This is a proposal, not an executed experiment.

Include outgoing eligibility references, incoming exceptions, a surviving independent duty, a permission plus a separate content requirement, repeated clause labels in different branches, nested alternatives, unavailable remote references, and an already complete negative control. Score standalone meaning, unsupported additions, unnecessary edits, optional-field damage, exact evidence, and no-op correctness separately; report raw success and accepted success, tokens, and latency. Use semantic criteria rather than one preferred wording, and review disputed boundaries before unmasking arms. OpenAI’s [evaluation guidance](https://developers.openai.com/api/docs/guides/evaluation-best-practices#how-to-read-evals) supports task-specific tests calibrated with human judgment. This small pilot could justify a narrower interface; it could not establish general legal completeness.
